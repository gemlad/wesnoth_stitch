# v1.1 — Plan of Action

v1.0.0 shipped (tag `v1.0.0`, Windows installer on Releases). v1.1 is a **quality-of-life
release against the shipped app**: six issues in the
[1.1 milestone](https://github.com/gemlad/wesnoth_stitch/milestone/7), no new architecture,
no new dependencies.

Live status is tracked in GitHub Issues, not here — `gh issue list --milestone 1.1`. This doc
is the *rationale and sequencing*: what each issue means in code, what it must not break, and
why the order is what it is.

## The one invariant everything here must respect

`symbolsFor(palette)` is index-aligned with `palette.colours`, which is sorted
dominant-floss-first (§5.2, §5.3). **The chart, the key and the preview all read that one
assignment**, which is what guarantees a key can never disagree with its chart — the single
bug in this codebase that would waste a whole stitching project rather than merely look bad.

Two issues below are within one step of breaking it: #90 (re-orders the key) and #56 (rewrites
the cell grid). Both are specified so the assignment is untouched. Neither may re-derive
glyphs, and neither may reorder `palette.colours` itself.

## The work, in order

### 1. #90 — Sort the floss key by DMC code

Today the key prints in palette order (dominant floss first). At the shop counter you are
reading down a list of codes, so it wants to be in code order.

- Sort **for display only**, inside `drawKeyPages`: build `{ index, colour, glyph }` rows,
  where `glyph` still comes from `symbolsFor(palette)[index]` at the *original* index, then
  sort the rows. `palette.colours` itself is never reordered.
- Comparator: numeric codes ascending (`3`, `310`, `3865` — not the string order that puts
  `3865` before `422`), then the non-numeric codes (`B5200`, `BLANC`, `ECRU`) alphabetically
  at the end. Those three are the only non-numeric entries in the dataset.
- Pagination is unaffected — same rows, different order. The "(1–40 of 47)" heading still
  reads correctly because it counts rows, not codes.
- Test: a palette whose code order and pixel-count order disagree, asserting the key rows come
  out in code order **and** that each row's glyph still matches `symbolsFor` at its original
  index. That second assertion is the one that catches the dangerous version of this change.

### 2. #91 — Sprite name in the header of every page except the cover

A loose page found on the floor should say what it belongs to.

- Draw the name **right-aligned on the existing heading baseline** — beside "Rows 0–68 /
  Cols 0–52" on chart pages, beside "Floss key" on key pages. Muted grey, same size band.
- **Do not add a new header line.** `CHART_HEIGHT_MM = PRINTABLE_HEIGHT_MM - TITLE_BAND_MM`,
  so growing `TITLE_BAND_MM` shrinks rows-per-page, re-tiles the chart and changes the page
  count. A cosmetic change must not move the tiling.
- Plumbing: `drawKeyPages` does not currently receive `ChartMeta`. Pass the title into both
  `drawKeyPages` and `drawChartPages` from `buildChartPdf`. The cover already has the name at
  22pt and is skipped (per the issue comment).
- Long names: truncate to the width left over after the tile heading, ellipsis, so it can
  never overlap.

### 3. #92 — "Page 2 of 12" in the footer of every page except the cover

**Numbering agreed with Gemma:** the cover counts as page 1 but carries no number, so the key
reads "Page 2 of 12" and the footer numbers always agree with the PDF viewer's page count.

- Total page count is only known once the cover, key and chart pages are all added, so this is
  a **post-pass in `buildChartPdf`**: `stampPageNumbers(pdf, font)` over `pdf.getPages()`,
  skipping index 0.
- Right-aligned on the licence footer's top line, same muted grey and 8pt, so it reads as one
  footer rather than two bits of furniture. `LICENCE_FOOTER_TOP_MM` is unchanged — nothing
  else has to move.
- Test: page count and per-page presence, plus "page 1 has no number".

### 4. #68 — Cover preview at true size on 14-count Aida

**Interpretation confirmed with Gemma:** this is the colour preview embedded on the chart
PDF's cover page (#46), not a new standalone PNG export.

- One stitch on 14-count Aida is 1/14" = **1.8143 mm**. Draw the preview image at
  `pattern.width × 1.8143 mm` wide, so it can be held against the fabric.
- **When it doesn't fit**, fall back to today's fit-to-box scaling. The box is the space
  between the finished-size block and the licence footer — roughly 170mm wide, and the height
  depends on how much the cover has already spent. A 72×72 sprite is 130mm square, so most
  sprites will make true size; the tall ones will not.
- **Say which one you are looking at.** A preview that is *sometimes* true size and never says
  so is worse than one that never is: caption it "Actual size on 14-count Aida" or "Reduced to
  fit — not actual size". Without this the feature is a trap.
- The raster's pixel size (`PREVIEW_TARGET_PX`) is independent of its drawn size; check the
  effective DPI at true size is still sharp (~700px over 130mm ≈ 137 dpi — fine) and raise the
  target if not.
- Test: assert the drawn width in points for a pattern that fits, and the fallback for one
  that cannot.

### 5. #66 — Search for a sprite

The browser lists every unit sprite in the set grouped by faction folder; finding "scout"
means scrolling.

- A search box at the top of `SpriteBrowser`, filtering on sprite **name and folder**,
  case-insensitive substring. Empty groups disappear; the group counts show matches.
- Purely client-side over the `SpriteSummary[]` already in memory — no IPC, no new channel.
- Keep it a controlled input inside `SpriteBrowser` (the list is that component's business);
  `App` does not need to know. Selection is unaffected — a selected sprite filtered out of view
  stays selected and stays charted.
- "No sprites match" state, so an over-typed search does not look like a broken app.
- Test: filtering and grouping behaviour on a fixture list.

### 6. #56 — Flip the pattern on the vertical axis

Mirror left-to-right, for stitchers who want the unit facing the other way.

- Add `flip: boolean` to `PatternSettings` (`shared/ipc.ts`) — it already crosses the process
  boundary, and the export must produce what the preview shows.
- Implement as one pure function in `shared/pipeline`: `flipHorizontal(pattern)` returning a
  new `StitchPattern` with each row reversed. **Palette and symbol assignment are untouched** —
  the cells move, the colours and glyphs do not.
- Apply it in exactly two places, both immediately after `convertSprite`: the renderer (so the
  Konva preview flips) and the export handler in `main/ipc.ts` (so the chart, cover preview and
  centre marks all flip together, since they all derive from the pattern).
- The raw sprite in `PreviewPane` does **not** flip. It is the reference you check the pattern
  against; flipping it too would remove the only way to see what the flip did.
- A toggle button in the `PatternView` control bar, beside "Fit".
- Ruler numbering: columns still count 0…n left to right on the flipped chart. That is correct
  — you stitch what is printed.
- Test: `flipHorizontal` is its own inverse; a 1-wide and a 0-wide pattern survive it.

### 7. Release 1.1.0

Follow [`RELEASING.md`](RELEASING.md) as written: bump `version` to `1.1.0`, run
typecheck/tests/lint locally (no CI, by choice), `npm run build:win`, publish the GitHub
Release with the installer attached.

Before tagging, a **manual pass on one exported chart** — the four export issues all change
the printed page, and no unit test can tell you whether the result is pleasant to stitch from.
Export a rich sprite, print page 1 of the chart at 100%, and check: key in code order with the
right glyphs, name and page number on every page but the cover, cover preview measuring true
against a 14-count ruler.

## Sequencing

```
#90 key sort ────┐
#91 header ──▶ #92 footer ──┤──▶ export UAT ──▶ 1.1.0 release
#68 cover preview ──────────┤
#66 search ─────────────────┤
#56 flip ───────────────────┘
```

#91 and #92 are sequential — both touch page furniture, and #92's post-pass is easier to write
once the header plumbing exists. Everything else is independent; #66 and #56 touch the renderer
and can run alongside the export work without conflict.

One branch per issue, as with Milestones 1–4.

## Risks

- **#56 and the export path.** The flip must be applied in main, not sent from the renderer as
  a flipped grid — `ExportRequest` deliberately carries identity, not pixels (§5.5), so that
  the exported chart and the preview cannot disagree. Sending the flipped pattern back would
  undo that.
- **#90's glyph indices.** Covered above; the test is the guard.
- **#91 and tiling.** Covered above; adding page furniture must not change `TITLE_BAND_MM`.
- **#68's honesty.** A preview that silently drops out of true size is the failure mode; the
  caption is not optional polish.
